# Story: Fix `tool_use` event_type PG enum drift

Status: done

**Completion note:** Ultimate context engine analysis completed - comprehensive developer guide created.

## Story

As a DB90 maintainer,
I want the PostgreSQL `public.event_type` enum to include `tool_use`,
so that Claude Code hook events can persist successfully and future per-tool event tracking is unblocked.

## Acceptance Criteria

1. Add a new Rails migration in `packages/api/db/migrate/` that extends `public.event_type` with `tool_use` using:
   ```ruby
   class AddToolUseToEventTypeEnum < ActiveRecord::Migration[8.1]
     disable_ddl_transaction!

     def up
       execute <<~SQL
         ALTER TYPE public.event_type ADD VALUE IF NOT EXISTS 'tool_use';
       SQL
     end

     def down
       # No-op: removing a PG enum value requires recreating the type.
       # Leaving 'tool_use' present is harmless.
     end
   end
   ```
2. A DB-backed persistence check for `tool_use` succeeds without raising `PG::InvalidTextRepresentation`.
   Note: in this codebase, a literal `ToolEvent.create!(organization: ..., occurred_at: ..., event_type: "tool_use")` still fails `tool_name` validation for a different reason, so the verification example must include a valid `tool_name` such as `claude_code`.
3. Ruby model enum values and PostgreSQL enum values are back in sync for `tool_use`:
   - `ToolEvent::EVENT_TYPES` includes `tool_use`
   - `public.event_type` includes `tool_use`
4. `packages/api/db/structure.sql` is regenerated by `bin/rails db:migrate` and includes `tool_use` in `CREATE TYPE public.event_type AS ENUM (...)`.
5. The migration is reversible in Rails terms: `down` is intentionally a documented no-op because PostgreSQL enum label removal requires type recreation and is out of scope for `db:rollback`.

## Dev Notes

### Business context

This is a narrow schema-consistency fix, not a product-behavior change.

- The active Claude Code hook ingest path already maps PostToolUse payloads to `event_type: "tool_use"`.
- The Ruby model already treats `tool_use` as valid.
- The database enum is the missing layer, so inserts currently fail at PostgreSQL type coercion time.
- This story is explicitly separate from historical `project_id` attribution work from AIX-247 and AIX-249. Do not mix in attribution, backfill-by-project, or broader telemetry redesign work.

### Current state and bug source

- `ToolEvent::EVENT_TYPES` already includes `tool_use`. [Source: `packages/api/app/models/tool_event.rb:12`]
- The Claude Code hook mapper emits `event_type: "tool_use"` for PostToolUse payloads. [Source: `packages/api/app/controllers/api/v1/ingest_controller.rb:141`]
- The original enum migration created `public.event_type` without `tool_use`. [Source: `packages/api/db/migrate/20260125224539_enable_timescale_db_and_create_enums.rb:36`]
- Current `structure.sql` also omits `tool_use` from `public.event_type`. [Source: `packages/api/db/structure.sql:76`]
- `packages/api/spec/models/tool_event_spec.rb` already asserts `tool_use` exists in the Ruby constant, but no spec currently proves the DB enum accepts it. [Source: `packages/api/spec/models/tool_event_spec.rb:15`]
- `packages/api/spec/requests/api/v1/ingest_spec.rb` already asserts raw Claude Code PostToolUse payloads are mapped to `tool_use`; that mapping test is not enough to catch the DB-layer failure because the request spec stubs the ingestion workflow instead of persisting a row. [Source: `packages/api/spec/requests/api/v1/ingest_spec.rb:78`]
- `ToolEvent` also validates `tool_name`, so any acceptance check that omits `tool_name` will fail before reaching PostgreSQL enum coercion. Use a valid `tool_name` in the persistence proof so the spec tests the right layer. [Source: `packages/api/app/models/tool_event.rb:21`]

### Technical requirements

1. Change only the DB enum surface needed for this bug:
   - new migration
   - regenerated `structure.sql`
   - focused spec update/addition for DB-backed verification
2. Do not change `ToolEvent::EVENT_TYPES` in this story unless you discover an unexpected mismatch while implementing. The constant already includes `tool_use`; this ticket is about bringing Postgres up to match Ruby.
3. Do not touch Swagger in this story. There is no controller contract change here; this is a schema repair behind an existing emitted value.
4. Do not rebuild the enum type in `down`. Follow the repo's existing pragmatic pattern for enum widening where rollback leaves the value present when removal is non-trivial.
5. Use `public.event_type` in the SQL, matching the explicit schema-qualified style already used by recent enum migrations in this repo.
